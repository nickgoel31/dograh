# Product assumptions and decisions

Decisions taken for the white-label product (brand: `PRODUCT_NAME`, default "Vocalis"). Update this file whenever one changes.

## Architecture (decided in Phase 2)
- **Product API lives inside the existing FastAPI app** as a router namespace: `/api/v1/product/*` (code in `api/product/`, tables in `api/db/product_models.py`). Why: shares the DB, auth helpers and workers with the minimum diff against upstream. Core files touched: `api/routes/main.py` (one include) and `api/alembic/env.py` (one import).
  - Note the prefix is `/api/v1/product`, not `/v1/product`, because the app mounts every router under `/api/v1`.
- **One workspace = two platform organizations** (live + test), stored in `product_workspaces.live_org_id/test_org_id`. Every core query for a request must use `ctx.org_id`, which resolves from the `X-Environment` header. Why: wallet, telephony, API keys, campaigns and runs are already keyed by `organization_id`, so Test/Live isolation needs no new column on core tables.
- **Roles are per membership** (`product_memberships.role`: owner/admin/developer/viewer), separate from the core `users.role`. The core role is left at `admin` for product users so existing platform code keeps working.
- **Sessions**: httpOnly cookie (`PRODUCT_SESSION_COOKIE`) carrying the existing JWT format, or `Authorization: Bearer`. Cookie is `Secure` unless `PRODUCT_COOKIE_SECURE=false` (needed for local HTTP dev).
- **Default environment is `test`** when the client sends no `X-Environment`, so nothing is billed or dialled by accident.
- **Public ids**: workspaces use `ws_…`; users `usr_…` (hash of the internal id). Internal integer ids are never returned.
- **Typed contract**: `python -m api.product.export_openapi vocalis-web/openapi.json` writes a product-only spec; `npx openapi-typescript openapi.json -o src/lib/api/schema.d.ts` regenerates the TS types.

## Front-end
- Source: `swarvoai/` (Vite + React 18), copied to `vocalis-web/` (original left untouched).
- `VITE_USE_MOCKS=true` serves the built-in sample data with no backend. With it `false` (default), sign-in is required and workspaces/Test-Live are real.
- **Only sign-in, workspaces and Test/Live are real so far.** Every other page still reads sample data via `src/lib/api/index.ts` until its module is built (Phase 3 onward). Sample data is therefore visible in real mode — do not treat it as the customer's data.

## Not done yet / open
- Email verification, password reset, Google sign-in, 2FA (none exist in the fork).
- New users get **no model/voice provider configuration**: the fork's signup provisions one via a managed external service; the product layer deliberately does not. Phase 3 must define server-side model presets per workspace.
- `OSS_JWT_SECRET` default is a placeholder; set a long random value before any deployment (tests currently warn about a 23-byte key).
- Rate limiting reuses the core limiter (Redis, degrades to per-process).
- Core tables are still created through the fork's normal migrations; the new migration `d1e2f3a4b5c6` has **not** been run against Postgres (see verification notes in the Phase 2 report).

## Agents (Phase 3, part 1)
- **Editing happens on the test workflow; "Go live" copies the published version into the live org** (created on first go-live, updated in place afterwards). `product_agents` holds both workflow ids plus emoji/colour/tone/business, status (`draft|live|paused`) and an integer `version` used as the ETag (`If-Match` header → friendly 409 `edited_elsewhere`).
- **Simple vs custom prompt**: simple agents recompile their prompt from fields via `api/product/prompt.py` (versioned, deterministic); writing a prompt switches the agent to custom and later field edits no longer overwrite it.
- **No LLM "generate my agent" yet.** The wizard creates from one of 8 data templates (`api/product/templates.py`) plus the user's description. LLM generation needs a server-side model config the product layer does not have yet.
- **Readiness** currently checks only: prompt present (blocker), business name (warn), voice chosen (warn). Knowledge, test-call and phone-number checks are added when those modules exist; the Publish tab still shows the demo's local checklist beside the real server check.
- **Pause/resume is a status flag only** for now; it does not yet stop inbound routing or campaigns (needs Phone Numbers/Campaigns, later phases).
- **Not yet real in the agent screen**: voice list (still demo voices), Call Flow editor (not saved; converter not written), Knowledge/Tools/Behavior/Phone/Test tabs, versions list, per-agent call stats (return 0).
- The core is reached through one seam, `api/product/gateway.py`. `CoreGateway` matches the core's real method signatures (checked) and the graph it generates passes the core's own DTO + graph validation (checked), but it has **not** been exercised against a real database.

## Voices and test calls (Phase 3, part 2)
- **Voice catalogue** (`api/product/voices.py`): adapters normalise provider voices. Today only the 222 `bulbul:v4-flash` voices are exposed. The provider's ids encode name, language and style, so those are filled in; **gender, age and accent are `null`** because the source data has none and guessing would be inventing facts. Add curated metadata (or another adapter) to fill them; the UI hides empty fields. Provider names are aliased (`Engine A`) and routing data never leaves the server. Favourites are per user (`product_voice_favorites`).
- **No voice samples yet.** Play buttons are disabled in real mode ("coming soon"); generating clips needs a provider key and object storage. Compare drawer plays nothing for the same reason.
- **Model setup is implemented; see `docs/MODEL_SETUP.md`.** Workspace orgs point at an operator-created default model profile; Brain presets and chosen voices become per-agent `model_overrides` copied from profiles (`api/product/models_config.py`). Without a default profile, agents show a "calls not set up" blocker and cannot go live or place test calls.
- **Quota check**: by reading `check_dograh_quota`, the external managed-service credit check only runs when a profile uses the platform's own managed provider. Profiles with the operator's own provider keys avoid it. The wallet admission check passes for organizations with the wallet disabled (the default for product orgs).
- **Test calls** (`WS /api/v1/product/agents/{id}/call`): cookie auth, origin check, workspace + role (developer or above), then a run is created in the **test** org against the draft graph and the platform's signalling takes over. Rejections accept the socket first and close with a reason code, because a socket closed before accept reaches browsers as a bare HTTP 403. In dev behind the Vite proxy set `PRODUCT_ALLOWED_ORIGINS=http://localhost:5174` (the proxy rewrites Host).
- **"Free" is by construction, not yet measured**: test orgs have the wallet off. Needs checking against a real run.
- **Typed-chat fallback and the Call Flow converter** are not built; the demo chat is hidden in real mode.

## Versions, call flow, conversations (Phase 3, part 3)
- **Versions**: listed from the platform's version history (no author/note exist there, so the UI shows status instead). Restore makes the chosen version the working draft; nothing goes live until Go live.
- **Call flow**: the editor's steps convert to/from the platform graph in `vocalis-web/src/lib/flowConvert.ts`. Step kinds live in ids (the platform drops unknown fields); steps the editor doesn't know are shown as "Advanced step" and kept byte-for-byte. A yes/no step is a conversation step whose two outgoing connections carry yes/no conditions (the platform has no branch node). "Hand to a human" is a plain conversation step until Tools wires the real transfer tool. The flow API validates with the platform's own validator and never lets the editor overwrite the agent's main prompt.
- **Conversations** (`/product/conversations`): scoped to the workspace *and* the active environment's organization (Test mode never lists live calls). Public ids are opaque and tamper-proof (`call_…`).
  - **Outcome mapping** (`api/product/conversations.py`) is rule-based on the platform's disposition text. The platform's disposition vocabulary was not fully enumerable from the code, so the rules are a **first guess to verify against real calls**.
  - **Not produced yet** (shown as empty, never faked): sentiment, AI summary, "why it failed" beyond a generic message, waveform peaks (plain audio player instead). These need the post-call analysis job.
  - **Reply speed** comes from the platform's recorded speed metrics when present.
  - **Cost** = minutes x `PRICE_PER_MIN` in Live, 0 in Test, split by the platform's vendor-cost proportions (phone is 0 until telephony). Replaced by real ledger numbers in the billing phase.
  - **Filters**: no filter = full SQL paging. Outcome/search filters scan the newest 2,000 calls (`truncated` is returned). The UI loads the newest 100 calls and filters inside them; CSV export streams everything.
  - **Audio** is a one-hour signed link from storage; never the stored path.

## Phone numbers (Phase 4)
- **Provider**: Twilio via the operator's own account (`PRODUCT_TWILIO_ACCOUNT_SID`, `PRODUCT_TWILIO_AUTH_TOKEN`; the vendor name never reaches customers). Live numbers are bought into that account with the platform's inbound webhook (`/api/v1/telephony/inbound/run`) already set; the platform then routes by the number's agent. The operator's credentials are copied into each workspace's telephony connection row, created on first use. `PRODUCT_NUMBER_MONTHLY_LOCAL` / `_TOLL_FREE` set the shown monthly price (default 0 = shown as "—"; billing arrives in Phase 5).
- **Test mode uses a sandbox** (fake numbers, never buys or rings anything). A sandbox number can be pointed at an agent but cannot receive real calls.
- **Assigning**: Live numbers only attach to agents that have been put live (the live copy); Test numbers attach to the test copy.
- **Opening hours + paused agents**: enforced by one small hook in the platform's inbound webhook (`routes/telephony.py`, calls `product/hours.py::inbound_gate`, fails open). A closed number or a paused agent plays a short message and hangs up. The message is spoken through the platform's generic error response, which on some providers is prefixed with an apology.
- **Fallback to a human is stored but not used yet.** Transferring a call needs the transfer tool, which arrives with Tools (Phase 6).
- **Spam reputation**: shown as "Not monitored yet"; no spam-score source is connected.
- **Bring-your-own SIP** is marked "Coming soon": the fork has no per-workspace SIP credential generation to show.
- **Not verified**: a real purchase, a real inbound call, or the hook against a live webhook (needs Postgres, Twilio credentials and a public URL). The Twilio number code (`number_providers.py`) is unexecuted; the sandbox path, assignment rules, hours logic and tenant scoping are tested (64 product tests).

## Money (Phase 5)
- **The platform's wallet does the debiting.** Each workspace's *Live* organization is switched to wallet billing on first use (`PRICE_PER_MIN`, `CURRENCY`, 60-second pulse, no overdraft). The platform already records one usage entry per finished call (minutes, rate, money taken); the product reads those entries and builds usage, the spend limit and invoices from them. Test mode never bills (the Test org has no wallet). There is no separate product ledger. Per-component vendor cost stays on the call record (used for the cost split on Conversations).
- **New workspaces start with 0 minutes**, so a live call is refused ("no remaining minutes") until they top up. `PRODUCT_FREE_MINUTES` grants welcome minutes once per workspace if you want a trial.
- **Top-ups (Razorpay)**: `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`. Order -> checkout -> signature-verified confirm, plus a signature-verified webhook as a backstop. Credits use the order id as an idempotency key, so confirm + webhook never double-credit (tested). Amount limits 100 to 100,000 (constants in `billing_router.py`). Stripe is not implemented; the provider seam is `payments.PaymentProvider`.
- **Spend limit** is monthly and measured on usage *value* (minutes x price, including minutes funded by free grants). At 80% the Billing page warns; at 100% the inbound gate plays a polite message and refuses new calls (checked in the same hook as business hours; fails open). It does **not** yet stop browser/campaign calls or an in-progress campaign mid-run.
- **Not done**: saved payment methods and **automatic top-up charging** (needs the provider's card/mandate vault; the setting is stored and presented as a reminder only); an in-app notification for the 80% / low-balance alerts (arrives with notifications in Phase 6).
- **Invoices**: one immutable invoice per finished month with charges (`product_invoices`), created when the list is opened, numbered `INV-YYYYMM-<id>` (the id is a database sequence; gaps are possible, and GST requires consecutive numbering, so confirm with your accountant). Taxable amount = money actually taken from the balance (minutes covered by free/prepaid grants are not invoiced). GST rate and seller details are **config you must set** (`PRODUCT_GST_RATE` default 18, `PRODUCT_SELLER_NAME/GSTIN/ADDRESS/STATE`, `PRODUCT_INVOICE_SAC`); CGST+SGST apply when seller and customer state codes match, otherwise IGST. I have not verified the SAC code or the tax treatment of advance top-ups; have them checked before issuing real invoices. Price is treated as tax-exclusive.
- **Not verified**: a real payment, the platform wallet against Postgres, or PDF layout by eye (tests check it is a PDF with the right numbers and scoping).

## Growth (Phase 6)
- **Test and Live are separate organizations, so knowledge and tools exist twice.** Adding a source or tool creates it in the Test org (the one customers manage) and a same-named twin in the Live org; deleting removes both. When an agent goes live, its document and tool links are translated to the Live twins by name. Names must therefore be unique per workspace (a clear "already taken" message is shown). A failed Live twin is silently tolerated and repaired the next time the agent goes live; it is **not** retried on its own.
- **Knowledge** reuses the platform's ingestion, chunking and search by calling its own handlers on behalf of the workspace org (`knowledge_router.CoreKnowledge`). Websites (auto re-read every 24h by default), PDFs (browser uploads straight to storage via one-time addresses; text-like files too), pasted text and Q&A (stored as text files, Q&A named "QA - ..."). "Test a question" returns the best matching passage and its source, not a written-out LLM answer. Needs an embeddings setting in the default model profile (`embeddings` key; see MODEL_SETUP.md). **Gaps ("questions with no answer") is not built**; the page says so.
- **Tools**: the one available integration is "Zapier, n8n or any web address" (a webhook tool). The ten named integrations (Google Calendar, HubSpot, Slack, Razorpay, ...) are listed as **Coming soon**; they need each provider's OAuth app and are not faked. Secret headers are stored by the platform and never sent back to the browser (shown as dots). "Test this tool" blocks private and internal addresses and does not forward the user's session. Built-in tools (transfer to a human, end call, SMS, email) are not wired yet, so **fallback-to-human is still stored but unused**.
- **Campaigns** (Live only; Test-mode dialing of your own numbers is not built): server-side contact check (E.164, duplicates, bad-row report, 10,000-contact cap), then the compliance gate: consent + Do-Not-Call attestation (no registry integration exists, so the customer attests and it is logged), calling windows only between 09:00 and 21:00 contacts' local time (`PRODUCT_CALL_WINDOW`), a live agent, then the platform creates the campaign from the cleaned CSV. Every create/start/pause/resume is written to `product_campaign_audit`. Counters (dialed/answered/voicemail/no answer/converted) are computed from the calls themselves using the same outcome rules as Conversations. The platform dials per its own schedule and retry settings. **Not verified**: campaign creation and CSV storage against the platform; per-contact time zones (the window uses one time zone for the whole list); the `campaign.completed` webhook (Phase 8).
- **Home** uses the single definition of success: booked, resolved, qualified or transferred. KPIs scan up to 5,000 calls in the range. The first-run checklist is derived from real state. The old "demo: new user" switch exists only in mock mode.
- **Notifications** are created once per cause (spend 80%, spend limit, low balance) when the Billing summary is read; there is no background job yet, so an alert appears the next time someone opens Billing, Home or any page that loads it. "Integration disconnected" and "campaign finished" alerts are not wired.
- **Agent screen**: the Knowledge and Tools tabs now save as you tick (to the test copy; Go live carries them over).
